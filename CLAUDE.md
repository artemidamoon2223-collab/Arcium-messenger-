# CLAUDE.md — Arcium Messenger

Анонимный E2E-мессенджер для Android: Rust-ядро в `crates/`, Anchor-программа
и Arcis-circuit в `arcium-psi/`, приложение в `android/`, документация и трекер
находок в `docs/`. Карта репозитория:
`.claude/skills/engineering-code-review/references/repo-map.md`.

С владельцем — по-русски. Код, комментарии, коммиты и PR — по-английски.

Здесь только правила, которые модель сама не знает. Не записывай сюда
состояние репозитория (сигнатуры, счётчики, деревья, статусы, историю PR): копия
расходится с кодом, а этот файл читается как истина (F-17). Смотри исходники и
GitHub.

---

## Режим работы

Zero-Idle: если информации хватает — начинай; вопросы, которые действительно
блокируют, собери в один запрос. Работу, о которой просил владелец, доводи до
конца: обычные ошибки, таймауты и упавшие инструменты диагностируй и обходи,
а намеренный запрет (закрытый доступ, защитное правило) не обходи — скажи, что
нашёл. Остановка оправдана, только когда без ответа владельца дальше нельзя.

Одобрение владельца нужно для:
- расходов: платные сервисы и API, включение модели Fable;
- production и необратимого: deploy; удаление веток, релизов, данных на сервере
  или файлов на `main`; публикация релиза, файла схемы или сообщения от имени
  владельца вне GitHub;
- мёрджа, изменения крипто/протокола, ослабления проверок (разделы ниже).

Без вопроса: push в рабочую ветку, PR, ревью и поиск субагентами на текущей или
более дешёвой модели, обновление continuity после разрешённой работы, удаление
своих временных файлов.

**Fable включает только владелец**: она намного дороже. Не выбирай её ни для
сессии, ни для субагентов и дочерних сессий — спроси. Уровень усилия выше
`high` тоже выбирает владелец.

**Отчёт.** Финальный отчёт о работе начинается тремя строками (промежуточные
сообщения — без них):

```
Сделано / Решено: [1–2 коротких предложения — результат]
Требует твоего решения: [что нужно одобрить, или «Ничего»]
Зоны неуверенности / Риски: [непроверенное, риски, или «Нет»]

---
```

Пиши для читателя без контекста: главное сначала, простые слова, без терминов,
придуманных по ходу работы.

## Криптографические правила

- **Сообщения:** XChaCha20-Poly1305 + Double Ratchet.
- **PSI / контакты:** только RescueCipher (arithmetic-friendly, совместим с MPC).
  XChaCha20/AES для PSI математически несовместимы с Arcium MPC; RescueCipher
  не для сообщений.
- **Хэш контакта** — обе стороны обязаны совпадать:
  `u64::from_le_bytes(sha256(phone.as_bytes())[0..8])`, little-endian, первые 8
  байт. Вход — только E.164 (`+79991234567`): `normalize_e164` в Rust,
  `normalizeE164` в TS, общие векторы
  `crates/core-crypto/tests/contact_hash_e164.tsv`. Номер без канонической
  формы не хэшируется.
- **OffChainCircuitSource:** `build/psi_intersect.arcis` хостится вне цепи по
  URL — константе программы; on-chain только этот URL и SHA-256 файла `.arcis`
  (его же пишет `build/psi_intersect.hash`). Не встраивай circuit в контракт
  (gas ×100). `CIRCUIT_HASH` в тестах — другой хэш: SHA-256
  `psi_intersect.arcis.ir`. Оба ≠ git SHA.
- **RescueCipher в Rust** (`crates/core-crypto/src/rescue.rs`) — заглушка на
  chacha20poly1305 с правильным API. Не заменяй на настоящий Rescue, пока
  circuit не задеплоен на Arcium testnet: arcium-client тянет Solana/Anchor и
  раздувает Android `.so` (M-3, NO-GO).

### Обращение с криптокодом
Криптологику, протоколы и параметры не меняй попутно: отдельная задача,
отдельный PR, явное указание владельца. Сюда относятся wire-форматы, метки и
параметры KDF, использование ключей, X3DH и ratchet, формат записей хранилища;
тексты ошибок, тесты и документация — нет. Заглушку не выдавай за
production-ready.

## Границы доказательств

Для отчётов, PR и коммитов. Компиляция, зелёный CI и зелёные тесты не
доказывают корректность и безопасность; если джоба глотает код возврата, её
цвет не значит ничего. Говори, чего результат не устанавливает, и что не
удалось проверить. Утверждение подкрепляй путём:строкой, SHA или именем теста.
Метки: `SOURCE_VERIFIED` (прочитано в исходнике), `RUNTIME_VERIFIED`
(наблюдалось при запуске), `INFERRED` (выведено, не наблюдалось),
`NOT_VERIFIED` (не проверено — почему).

## Анализ безопасности

Только признанные классы угроз; процедура и список — навык
`arcium-security-review`. Псевдонаучные модели
(phase/frequency/Fibonacci/Mishin/quasicrystal/PhaseSCA) не используем: они не
дают проверяемых выводов.

## Окружение

Песочница не пускает на api.devnet.solana.com, Anchor и Solana CLI в ней нет:
deploy, airdrop и devnet-тесты отсюда не запускай. Deploy на devnet —
`docs/HOME-DEPLOY.md`. Хук `.claude/hooks/guard.py` спрашивает владельца перед
известными формами таких команд; правило действует и без него.

## Команды проверки

Как в `.github/workflows/arcium-ci.yml` и `.devcontainer/setup.sh`:

```bash
cargo test --workspace --locked
cargo clippy --workspace --locked -- -D warnings
cd arcium-psi/tests && npx tsc --noEmit
cd arcium-psi/tests && npx mocha --require ts-node/register 'src/crypto.test.ts'
```

Задача не закрыта без проверки: 0 упавших тестов, `tsc` без ошибок, если
трогал TS, в diff только запрошенное.

**Готово, когда.** До начала нетривиальной задачи запиши, какая команда и какой
её вывод будут значить «готово» (`Готово, когда: <команда> → <строка вывода>`),
и что трогать нельзя. В отчёте и PR приводи итоговые строки вывода этих команд
дословно (`test result: ok. 580 passed; 0 failed`), а не пересказ: владелец
сверяет одну строку, а не код.

**Две попытки.** Если проверка не проходит после двух попыток исправления,
остановись: напиши владельцу, что мешает, и предложи другой подход.

## Ревью и CI

- CI только детерминированный: никаких вызовов LLM и их ключей в воркфлоу без
  явного указания владельца.
- Блокирующую проверку не делай advisory (`continue-on-error`, `|| true`,
  проглоченный код возврата) без явного указания владельца.
- Нетривиальное изменение проходит `engineering-code-review`; чувствительное к
  безопасности (крипто, протокол, durable-состояние, идентичность, сеть,
  FFI/Android, PSI/on-chain, CI, зависимости, секреты) — ещё и
  `arcium-security-review`. Обычно делай их сам. Изменение в крипто,
  протоколе, сети, FFI или CI ревьюит отдельный агент со свежим контекстом:
  дай ему diff и навыки, а не свой пересказ, — автор свой код не видит со
  стороны. Ревью — анализ, а не доказательство.

## Версии — не менять без причины

- arcium-client 0.10.4; arcium-anchor 0.10.4 требует anchor-lang `=1.0.2`
- arcis 0.10.4 (генерирует `.arcis.ir`)
- @coral-xyz/anchor ^0.30.1, @arcium-hq/client ^0.10.4
- ml-kem `0.3` (не 0.2)
- Версии CI — из defaults `arcium-hq/setup-arcium@v0.10.4`; сверяйся с его
  README, прежде чем бампать.

## Постоянные ограничения

- Мёрдж: обычный merge commit (не squash) и только по явному указанию
  владельца, называющему PR. Зелёный CI указанием не является. Хук
  `.claude/hooks/guard.py` спрашивает владельца перед известными путями мёрджа
  и записи в `main`; это страховка, а не замена правилу.
- Состав required status checks на `main` доступными инструментами не читается;
  не выводи его по косвенным признакам.
- RUSTSEC-2025-0009 (ring 0.16) и RUSTSEC-2023-0071 (rsa 0.9): ignore в
  `.cargo/audit.toml` снимать, только когда upstream выпустит исправление;
  пересмотреть на security-аудите (как и RUSTSEC-2026-0387).
- RUSTSEC-2026-0387 (crypto-bigint 0.5): ignore действует только вместе с guard
  `.github/scripts/check_rustsec_2026_0387.py`; снять оба, когда crypto-bigint
  0.5 уйдёт из `Cargo.lock`.
