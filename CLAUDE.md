# CLAUDE.md — Arcium Messenger

Постоянное ядро: только то, что нужно почти в каждой сессии. Специализированные
процедуры лежат в `.claude/skills/` и подключаются по необходимости.

Общение с разработчиком — на русском. Код, комментарии, сообщения коммитов и
тела PR — на английском.

## Режим работы

### Zero-Idle
- Перед началом изучи доступный контекст: задание, `CLAUDE.md`, навыки,
  исходники, GitHub. Вопросы, которые действительно блокируют работу, собери в
  **один** общий запрос; если информации достаточно — начинай сразу.
- Дальше иди без остановок через авторизованные шаги: реализация, проверка,
  исправление, отчёт. Не спрашивай разрешения на рутинные промежуточные шаги.
- Одобрение владельца нужно для этих действий, и Zero-Idle их не снимает:
  - расходы: платные сервисы и API, включение модели Fable (раздел ниже);
  - production и необратимое: deploy; удаление веток, релизов, данных на
    сервере или файлов на `main`; публикация релиза, файла схемы или
    сообщения от имени владельца вне GitHub;
  - операции владельца ниже: мёрдж, изменение крипто/протокола, ослабление
    проверок.
- Без вопроса, как рутина: push в рабочую ветку, создание PR, ревью и поиск
  субагентами на текущей или более дешёвой модели, обновление continuity
  после разрешённой работы, удаление своих временных клонов и файлов.

### Модель Fable — включает только владелец
Fable 5.2 расходует намного больше токенов и денег. Поэтому переключать на неё
работу может только владелец. Не выбирай Fable сам: ни для сессии (`/model`,
ключ `model` в настройках), ни для субагентов и дочерних сессий (параметр
`model`). Если задача, по-твоему, требует Fable, спроси владельца и жди
ответа; остальную работу продолжай на текущей модели. Уровень усилия
(`/effort`) тоже задаёт владелец: для долгих самостоятельных задач полезен
`high`, а `xhigh` и `max` — только по его решению.

### Доводи работу до конца
Не останавливайся, пока должен работу, о которой просил владелец. Короткие
статусы и вопросы по открытым решениям уместны, но то, что не зависит от
ответа, продолжай без лишних остановок. Вместо предложения «могу продолжить»
переходи к следующей части задачи. Обычные препятствия — ошибки, таймауты,
пустые результаты, упавшие инструменты — сначала диагностируй и обходи
доступными средствами: повтори, исправь запрос, возьми другой инструмент.
Препятствие, поставленное намеренно (файл, который нельзя трогать, закрытый
доступ, защитное правило), не обходи: скажи, что нашёл, и ищи другой
безопасный путь. Остановка до конца задачи оправдана редко: когда без ответа
владельца дальше нельзя или препятствие намеренное. Это не отменяет
подтверждения перед опасными и необратимыми действиями.

### Пиши понятно
Пиши для умного читателя без контекста: он не видел твоих вызовов
инструментов, рассуждений и открытых файлов. Главное — в первых предложениях.
Простые слова, полные предложения, действительный залог, одно и то же слово
для одной и той же вещи. Не используй термины и сокращения, придуманные по
ходу работы. Связанные мысли — абзацем, отдельные пункты — списком. Лишние
детали опускай, ключевой контекст оставляй.

### Отчёт владельцу: три строки
Финальный отчёт о работе начинается так (короткие промежуточные сообщения —
без этой шапки):

```
Сделано / Решено: [1–2 коротких предложения — результат]
Требует твоего решения: [что нужно одобрить, или «Ничего»]
Зоны неуверенности / Риски: [непроверенное, риски, или «Нет»]

---
```

Ниже разделителя — технические детали, логи, тесты, объяснения и метки
доказательств (раздел «Границы доказательств и формулировок»). Владелец должен
понять результат по первым трём строкам; «Нет» ставь, только если
непроверенного действительно нет.

### Сначала навыки
Перед автоматизацией проверь, не решает ли задачу существующий навык
(`.claude/skills/`) или slash-команда (`.claude/commands/`). Процедуры для
модели пиши краткими Markdown-инструкциями; Python/Bash/Node — только когда
нужно детерминированное исполнение или принуждение (как `.claude/qc/qc.py`).
Не дублируй существующие скрипты и проверки.

Команды (`.claude/commands/`, вызывает только пользователь):
`/capture-workflow [name]` — превратить завершённый в этой сессии процесс в
команду; `/weekly-retro` — ретроспектива за 7 дней с предложениями правил;
`/sync-project-context <заметки>` — перенести принятые решения в документацию.

## Что за проект

Анонимный E2E-мессенджер для Android. Четыре слоя защиты: Tor onion (arti;
пока не подключён, F-15), X3DH + Double Ratchet, шифрованный SQLite
(XChaCha20-Poly1305), Arcium MPC для приватного поиска контактов (PSI).

Ориентация: Rust-ядро в `crates/`, Anchor-программа и Arcis-circuit в
`arcium-psi/`, Android-приложение в `android/`, документация и трекер находок в
`docs/`. Подробная карта намеренно не живёт здесь — см.
`.claude/skills/engineering-code-review/references/repo-map.md`.

❌ Не инвентаризируй состояние репозитория в этом файле: здесь не место
сигнатурам, счётчикам файлов и воркфлоу, деревьям каталогов, статусным
таблицам, спискам веток и истории PR. Такие копии расходятся с репозиторием по
построению, а файл читается каждой сессией как истина (находка F-17 в
`docs/SECURITY-FINDINGS.md`). Читай исходники и GitHub. Одиночное версионное
ограничение, записанное как предупреждение, инвентарём не является.

## КРИТИЧЕСКИЕ криптографические правила

### Два РАЗНЫХ слоя, не путать
- **Сообщения:** XChaCha20-Poly1305 + Double Ratchet
- **PSI / контакты:** ТОЛЬКО RescueCipher (arithmetic-friendly, совместим с MPC)
- ❌ НИКОГДА не используй XChaCha20/AES для PSI — математически несовместимо с Arcium MPC
- ❌ НИКОГДА не используй RescueCipher для сообщений: он нужен для арифметики
  MPC, в Rust это заглушка (`rescue.rs`), а сообщения защищает Double Ratchet

### Хэш контакта — канонический стандарт, обе стороны ОБЯЗАНЫ совпадать
```
u64::from_le_bytes( sha256(phone.as_bytes())[0..8] )
```
Little-endian, первые 8 байт.
Вход — номер строго в E.164 (`+79991234567`): `normalize_e164` в Rust и
`normalizeE164` в TS, общие векторы `crates/core-crypto/tests/contact_hash_e164.tsv`
(D-010). Номер без канонической формы не хэшируется.

### OffChainCircuitSource
- Скомпилированный circuit `build/psi_intersect.arcis` хостится вне цепи (по
  URL — константе программы), НЕ загружается on-chain
- On-chain хранятся только этот URL и 32-байтный SHA-256 файла `.arcis` (его
  же пишет `build/psi_intersect.hash`); узлы Arx сверяют скачанный файл с ним
- ❌ НИКОГДА не встраивай circuit в смарт-контракт (раздувает gas в 100x)
- Два разных хэша, оба ≠ git commit SHA: хэш на chain — SHA-256 `.arcis`;
  `CIRCUIT_HASH` в тестах — SHA-256 `psi_intersect.arcis.ir` (отпечаток
  версии circuit)

### RescueCipher в Rust (`crates/core-crypto/src/rescue.rs`)
- Сейчас STUB на chacha20poly1305 как placeholder; API правильный
- НЕ заменяй на настоящий Rescue пока circuit не задеплоен на Arcium testnet
- Причина: arcium-client тянет весь Solana/Anchor стек → раздувает Android .so

### Обращение с криптокодом
Криптографическую логику, протоколы и параметры не меняй попутно с другой
задачей: отдельная задача, отдельный PR, явное указание владельца. Сюда
относятся wire-форматы, метки и параметры KDF, использование ключей, X3DH и
ratchet, формат записей хранилища. Тексты ошибок, тесты и документация сюда
не относятся. Не выдавай
экспериментальный или заглушечный код за production-ready.

## Границы доказательств и формулировок

Действует во всех отчётах, телах PR и сообщениях коммитов.

- Успешная компиляция НЕ доказывает runtime-корректность, безопасность или
  корректность протокола.
- Зелёный CI-чек доказывает только то, что джоба доехала до конца. Если джоба
  маскирует ненулевой код возврата, её цвет не доказывает ничего —
  доказательством является лог.
- Тест-грин ≠ безопасно. Схема-валидно ≠ верно. Хорошо оформлено ≠ верно.
- Всегда указывай, чего результат НЕ устанавливает.
- Если шаг нельзя проверить (нет сети, toolchain или прав) — скажи это прямо;
  не выводи ответ по косвенным признакам и не выдавай догадку за факт.
- Собственный пересказ ранее сделанной работы доказательством не является.
  Claim подкрепляется путём с номером строки, SHA коммита или именем
  прошедшего теста. Перепроверяй номера строк перед цитированием.
- Метки в отчётах и ревью: `SOURCE_VERIFIED` — прочитано в исходнике
  (путь:строка); `RUNTIME_VERIFIED` — наблюдалось при запуске (команда, тест
  или строка лога); `INFERRED` — выведено, но не наблюдалось (из чего);
  `NOT_VERIFIED` — не проверено (почему и что проверило бы).

## Анализ безопасности

Использовать ТОЛЬКО признанные классы угроз: timing/cache/power/EM
side-channel, X3DH/replay/OPK protocol bugs, key/nonce misuse и zeroization,
согласованность durable-состояния (crash, rollback, дубликаты), PSI/MPC
correctness, on-chain access control, traffic analysis, FFI boundary, supply
chain, CI integrity (ложно-зелёные проверки). Процедура — навык
`arcium-security-review`.

❌ НЕ добавлять псевдонаучные модели — они не дают проверяемых выводов
(phase/frequency/Fibonacci/Mishin/quasicrystal/PhaseSCA).

## Ревью и CI

- GitHub CI только детерминированный: тесты, сборки, анализаторы. ❌ Никаких
  вызовов LLM-провайдеров и их API-ключей в воркфлоу; вернуть такое — только
  по отдельному явному указанию владельца.
- ❌ Не превращай блокирующую проверку в advisory (`continue-on-error: true`,
  `|| true`, проглоченный код возврата) без явного указания владельца:
  такая проверка зелёная всегда и ничего не доказывает.
- Перед приёмкой владельцем: нетривиальное изменение проходит инженерное
  ревью (`engineering-code-review`, `references/karpathy-review.md`);
  изменение, чувствительное к безопасности (крипто, протокол, durable-
  состояние, идентичность, сеть, FFI/Android, PSI/on-chain, CI, зависимости,
  секреты), — ещё и `arcium-security-review`. Оба ревью выполняются локально
  в сессии Claude Code, без API-ключа. Делай их сам; отдельного агента-
  ревьюера запускай только для security-ревью изменений крипто, протокола,
  сети или FFI, где нужен взгляд без твоих выводов: он стоит сотни тысяч
  токенов.
- Модельное ревью — анализ, а не доказательство. Тесты и runtime-
  доказательства по-прежнему обязательны, решение о мёрдже — за владельцем.

## Постоянные ограничения

- Мёрдж: обычный merge commit (НЕ squash) и только по отдельному явному
  указанию владельца. Зелёный CI указанием не является.
- Branch protection на main — owner-only. Состав required status checks
  доступными инструментами не читается; не выводи его по косвенным признакам.
- M-3 (NO-GO): RescueCipher stub в Rust остаётся — настоящий Rescue есть только
  в TS `@arcium-hq/client`, Rust-крейта без Solana-стека нет.
- RUSTSEC-2025-0009 (ring 0.16.x) и RUSTSEC-2023-0071 (rsa 0.9.x): REVISIT AT
  SECURITY AUDIT. Ignore в `.cargo/audit.toml` снимать только после появления
  исправленной версии upstream.
- RUSTSEC-2026-0387 (crypto-bigint 0.5.x): REVISIT AT SECURITY AUDIT. Ignore
  действует только вместе с guard `.github/scripts/check_rustsec_2026_0387.py`;
  запись и guard снять, когда crypto-bigint 0.5 уйдёт из `Cargo.lock`.
